## B. Places where I'd change or interpret a decision (flagged, built, easy to reverse)

1. **The display sign lives on the plan line, not on `line_map`.**
   - The prompt puts the sign on `line_map`, one per mapped account. Then two accounts mapped to
     Revenue could carry different signs, and Revenue's total would mix them.
   - Your decision describes it as "a display sign per plan line". So I put `display_sign` on
     `fpa.plan_line_defs`, one per line:
     - Revenue and the three profit lines: −1, so revenue shows positive;
     - the cost lines: +1.
   - `line_map` only says which line an account belongs to.
   - If you want a per-account sign as well, that is a separate decision.

2. **A mapping choice for accounts that aren't in the P&L: "Not in the P&L (excluded)".**
   - The problem: a full trial-balance file includes bank, debtors, VAT and other balance-sheet
     accounts. With only the binding list, those accounts would stay Unmapped forever, so "mapping
     complete" could never be reached.
   - What I added: one extra row, `excluded`. The user has to pick it per account; it is never
     applied automatically.
   - Excluded accounts are listed on the mapping screen, but they stay out of every P&L line and
     out of variance.
   - **This adds to your plan-line list.** Say no, and I'll drop the row and tell users to import
     P&L accounts only.

3. **Unmapped is kept out of the calculated lines.**
   - Gross profit, Operating profit and Net profit add up only the mapped income and cost lines.
   - Unmapped is shown as its own line, in the file's sign (debits positive), and is never dropped.
   - While anything is unmapped, the KPI strip and Compare will say the profit figures are
     incomplete.

4. **Budget amounts are stored in the same sign as actuals** (debits positive, so a revenue budget
   is negative in `plan_lines`).
   - Variance and the screens apply the display sign, so one rule covers actual and budget.
   - The Plan page will let people type revenue as a positive number and convert it.

5. **Rounding.**
   - The rule lives in `src/engine/rounding.ts`, pure TypeScript with tests, as you decided.
   - `create_budget_from_actuals` has to apply the same rule in SQL, because the server must not
     trust amounts worked out in the browser.
   - Both are tested against one shared file of cases, `db/tests/fixtures/rounding_cases.json`, and
     Python's `Decimal` checks that file independently.
   - **Rounding is half away from zero**, which is what Postgres's `round()` does, so €0.005 becomes
     €0.01 and −€0.005 becomes −€0.01. Tell me if you want banker's rounding instead.
   - Month 12 takes `round(annual) − (the sum of the 11 rounded months)`.

6. **A new `origin` value, `from_actuals`, on `plan_lines`**, for lines copied from actuals by the
   budget function.
   - The other values are still `actual`, `driver` and `manual`.
   - Editing a line by hand sets it to `manual`.
   - This adds a value to the B2 enumeration list.

7. **Failed imports are not written to `sync_runs`.**
   - Any failure rolls back the whole transaction, and that includes the log row. So the table only
     ever holds successful runs.
   - The `status` column allows `succeeded` and `failed`, but in Phase 1 only `succeeded` is ever
     written.
   - The UI shows the failure and its reason. Nothing is saved, and the UI says so.

## C. Missing from the scope, added

1. **Account names.** Nothing stores the optional account name from the file, but the mapping screen
   needs it. I added `account_name` to `actuals_monthly`, nullable, at most 200 characters. The map
   shows the name from the latest month.
2. **Where the CSV connection comes from.** By the Phase 0 rule, only owners add connections, and an
   import needs one.
   - Connect will offer an owner "Add CSV connection".
   - An editor on an entity with no CSV connection is told to ask an owner.
   - `import_actuals` refuses a connection that isn't CSV, or one that is disabled.
3. **Input the server refuses rather than changes:**
   - amounts with more than two decimals;
   - months that aren't written `YYYY-MM-01`, which the browser converts from `YYYY-MM` or a date;
   - months before January 2000, or after the current month.
4. **The 5 MB limit is checked twice:**
   - on the file, in the browser;
   - on the rows sent, on the server, because the server never sees the file.
5. **Budget from actuals refuses when:**
   - any month in the 12-month window has no actuals at all;
   - any account with actuals in the window is unmapped.
   - In both cases the error says why.
6. **Line-map writes.**
   - Both the direct table route (allowed since Phase 0, editor or owner) and the new function
     `set_line_map` are kept.
   - Both now have to name a mappable line: a foreign key into `plan_line_defs` stops anyone mapping
     to a calculated line, to Unmapped or to a made-up key.
   - `set_line_map`, `account_map`, `unmapped_accounts`, `variance` and
     `create_budget_from_actuals` run as the caller (SECURITY INVOKER), so row security applies to
     them.
   - Only `import_actuals` runs with the owner's rights (SECURITY DEFINER), because the API can't
     write actuals directly.
7. **The migration number.**
   - The next number is 0003. The 0002 VAT draft is still unapplied, and the Phase 0 migration
     planner refused to apply any file after an unapplied draft.
   - I changed the rule:
     - a `*_DRAFT.sql` file is never applied and no longer blocks later files;
     - to apply a draft, it must be renamed to a new number after the last applied one;
     - the planner refuses any pending file numbered below a file already applied, which keeps the
       order guarantee.
   - The VAT draft would become something like `0004_fpa_vat_rules.sql` when you approve it.
8. **The KPI definitions document** (`docs/kpi-definitions.md`). I wrote it now, from your wording,
   so you can sign it off during the 1A review. Nothing is wired to it until 1E.
