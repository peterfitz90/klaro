## 4. Phase 1 preview: Ledgrly journals into monthly balances (report only)

**Shape.** `public.journals` is one row per double entry: `company_id, date, debit_account,
credit_account, amount numeric(12,2), vat_code, transaction_currency, fx_rate, …`. Account codes are
text matching `chart_of_accounts(company_id, code, name, account_type, category)`. Opening
positions sit in `prior_year_balances(company_id, year_end_date, account_code, debit_balance,
credit_balance)` and in opening journals. Locked periods are in `financial_periods`.

A monthly balance per account is a debit-normal net movement:
`sum(amount where debit_account = code) - sum(amount where credit_account = code)`, grouped by
`date_trunc('month', date)`. This is the same sign rule as the one existing server-side sum,
`public.nominal_balance_as_of(company_id, codes[], as_of)`: SECURITY INVOKER, so journals' own row
security applies; EXECUTE by authenticated only (`supabase/add_nominal_balance_rpc.sql`).

**What exists today.**
- No view or function produces monthly balances per account. Every Ledgrly report (TB, P&L, P&L
  trend, BS, GL) is aggregated in the browser over all journal rows, fetched page by page
  (`src/shared/fetchAllRows.js`; GLReport App.jsx 8868+, TB 9080-9122, BS 9200-9240;
  `buildPnL` in `src/shared/pnl.js`, `opexByMonth` in `src/shared/opex.js`).
- `nominal_balance_as_of` is the only server-side sum (used for cash balances and Luca's overview).
- Server routes that read journals all run with the caller's own token, so RLS applies:
  - `api/chat.js` (Luca, `requireCompanyMember`) with tools in `api/_tools.js`: `get_report`
    (pnl / trial_balance / balance_sheet JSON, paged to 20,000 rows with a `truncated` flag) and
    `get_forecast` (commit 73a5e57).
  - `api/statements-pdf.js` and `api/statements-approval.js` via `api/_statements-data.js`.
- Row-limit note: journals are paged everywhere. Some smaller reads are not paged and rely on
  staying under 1,000 rows: `chart_of_accounts` in `_tools.js` and `forecast.js`,
  `prior_year_balances` at App.jsx:87, `ap_invoices`. Klaro must not copy those patterns.

**Possible read routes (Peter to choose in Phase 1; nothing built or touched):**
1. **A new SECURITY INVOKER function in Ledgrly**, for example
   `public.monthly_account_balances(company_id, from, to)` returning
   `(account_code, period, net_movement)`, aggregated in SQL so there is no row-limit exposure.
   The Klaro sync would call it with the user's own Clerk token, so Ledgrly's RLS decides access.
   This is a change to Ledgrly, so it needs Peter's approval.
2. **No Ledgrly change.** The Klaro sync pages through `journals` with the user's token and
   aggregates in Klaro's own server. This is slower and moves every journal row over the wire.
3. **The same function as option 1, but called by a Klaro server job with service_role.**
   This bypasses RLS, so Klaro would have to check Ledgrly company membership itself. Not
   recommended.

Whichever route: the write side stays in `fpa` (`actuals_monthly` through a function), keyed by
`connections.id`, with `entities.ledgrly_company_id` as a plain uuid and no foreign key.

## 6. Anything that would break the plan

Nothing blocks. Points to carry forward:

1. **Single session mode**: sign-out in one app signs out of all of them in that browser. That's
   acceptable, but users should be told.
2. **Clerk redirects default to Ledgrly** (above). Handled in B4 by explicit redirects.
3. **The connector's confirmation prompt.** The fpa schema needs `DELETE` grants and policies
   (editors delete plan rows). In the past the connector has asked for confirmation on
   destructive-looking SQL, and that prompt expires after 10 minutes. The B2 tests build the
   word at run time where they can. If a prompt does appear, it needs Peter at the screen.
4. **Exposing `fpa` must wait until it exists** (B3), as stated.
